SQLD 개인 학습 앱 — Codex 개발 마스터 명령서

너는 이 프로젝트의 구현 책임자다. 제품 기획, SQLD 교육 설계, 콘텐츠 제작·검증, UX/UI 디자인, 앱 개발, 데이터 설계, QA, 빌드와 인수인계까지 수행하라.
기획서만 작성하거나 화면 목업·일부 샘플만 만들고 종료하지 말고, 실제 학습 가능한 앱을 구현하고 검증하라.
단, 실행하지 않은 테스트, 확인하지 않은 시험 기준, 검수하지 않은 문항을 완료했다고 보고하지 마라.

0. 제품 목적과 우선순위

목적: 내가 이 앱으로 SQLD를 공부하고, 개념을 이해·암기하고, 처음 보는 적용 문제를 풀 수 있도록 돕는 개인용 학습 도구다.

사용자는 컴퓨터공학 전공이지만 SQLD 내용을 모두 안다고 가정하지 마라. 용어부터 쉽게 설명하되 시험 수준의 정확성을 유지하라.

주요 사용 환경은 Galaxy S24+와 Galaxy Tab이다. 휴대폰 세로 화면, 태블릿 가로·세로, 분할 화면을 고려하라.

핵심 흐름: 필기형 개념 노트 → 짧은 회상 퀴즈 → 적용 문제 → 단계별 해설 → 오답·별표·취약 개념 복습 → 처음 보는 모의고사 → 약점 보완.

우선순위: 콘텐츠·채점의 정확성 > 학습 기록 보존 > 학습 동선·가독성 > 시각적 완성도 > 부가 기능.

아름다운 UI는 필수다. 다만 화려함 때문에 공부하기 어려워지면 잘못된 디자인이다.

합격 보장, 근거 없는 합격 확률, 실제 수험생 검증 없는 학습 효과 수치를 만들지 마라.

1. 작업 시작: 저장소 확인, 범위 확정, 계획

현재 작업 폴더, 기존 코드, AGENTS.md, 의존성, 빌드 환경, 테스트 실행 가능 여부를 먼저 확인하라.

기존 프로젝트가 있으면 사용자 코드·설정·데이터를 보존하고 현재 구조를 우선 활용하라. 동의 없이 전면 재작성·파괴적 초기화하지 마라.

신규 Android 프로젝트의 기본안은 Kotlin + Jetpack Compose + Material 3 + Room + DataStore다. 기존 Flutter/React Native 프로젝트라면 동등한 요구사항을 만족하도록 유지할 수 있다.

실제로 호환되는 안정 버전을 조사·선택하고 버전·선정 이유·빌드 방법을 기록하라. 무조건 최신이라는 이유로 프리뷰 버전을 쓰지 마라.

앱 사용에 서버, 회원가입, 결제, 유료 API, 런타임 LLM 호출이 필요하지 않게 하라. 학습 콘텐츠와 핵심 기능은 설치 후 오프라인에서 동작해야 한다.

광고·커뮤니티·랭킹·구독·원격 관리자·자동 클라우드 동기화는 이번 범위에서 제외한다.

비용 발생, 계정 생성, 자격증명 사용, 외부 공개 배포, 원격 저장소 push, 파괴적 변경은 별도 승인 없이 실행하지 마라.

합리적으로 결정 가능한 구현 사항은 결정 근거를 남기고 진행하라. 이미 정한 요구사항을 반복해서 질문하지 마라.

아래 요구사항에 ID를 붙이고, 요구사항 → 구현 위치 → 콘텐츠 → 테스트 → 증거를 연결하는 추적표를 작성하라.

AGENTS.md에는 핵심 제약, 실제 빌드·검증 명령, 데이터 보존 규칙, 콘텐츠 검수 규칙과 관련 문서 경로를 간결하게 남겨라.

2. SQLD 시험 기준과 자료 출처 검증

작업 당일 한국데이터산업진흥원 데이터자격검정의 SQLD 종목 안내, 출제기준, 변경 공지, 자료실·정오표를 확인하라.
시행기관 자료를 최우선으로 하고, SQL 문법은 해당 DBMS 공식 문서를 근거로 검증하라.

초기 검토용 시험 설정:

1과목: 데이터 모델링의 이해 — 10문항, 20점.

2과목: SQL 기본 및 활용 — 40문항, 80점.

총 50문항, 문항당 2점, 시험시간 90분.

총점 60점 이상이면서 각 과목 득점률 40% 이상일 때 합격 기준 충족.

위 구성에서는 1과목 최소 4문항, 2과목 최소 16문항 정답이 과락 회피 기준이다. 이것만으로 총점 합격은 아니다.

이 값들을 최신 공식 원문 확인 없이 '공식 최신 검증 완료'로 표시하지 마라.
시험 규칙은 ExamSpec으로 분리하여 출제기준 버전, 적용일, 출처, 확인일을 저장하고 변경할 수 있게 하라.
기존 시험 세션은 시작 당시 ExamSpec을 보존하라.
공식 사이트가 열리지 않으면 접근 실패와 대체 자료를 기록하고 확인 가능한 개발은 계속하되, 최종 보고서에서 미확인 항목을 숨기지 마라.

모든 참고 자료에 sourceId, 발행기관, 제목, URL, 버전/발행일, 확인일, 관련 절, 활용 범위, 이용 조건을 기록하라.
접속하지 않은 URL을 근거처럼 만들어 넣거나, AI가 작성한 문제에 실제 시험 연도·회차를 붙이지 마라.
시험 일정은 사용자 설정으로 관리하고, 확인된 일정과 직접 입력한 목표일을 구분하라.

참고 진입점과 검증 시 주의사항:

데이터자격검정: https://www.dataq.or.kr/ 및 https://www.dataq.or.kr/www/sub/a_04.do
이 명령서 작성 시점인 2026-09-14 조회에서는 공식 상세 페이지에 접근하지 못했다. 최신 원문 확인을 다시 시도하라.

시험 구성 교차 확인용 출판사 안내: https://company.eduwill.net/pr/newsInfo?bIdx=315451&page=&searchTarget=all
2026 대비 교재 안내에 포함된 시험 설명이며 시행기관의 최신 공지를 대체하지 않는다.

범위 교차 확인용 교재 목차: https://wikibook.co.kr/sqld2026/
출판사의 학습 목차이므로 공식 범위와 동일하다고 가정하거나 본문·문항을 복사하지 마라.

자료가 열리지 않거나 개정되면 실제 확인한 경로와 버전을 기록하라. 위 주소가 모든 세부 문항의 근거를 대신하지 않는다.

3. 기출·복원·창작 문제의 구분

'인터넷에 기출이라고 적혀 있다'는 이유로 공식 기출로 취급하지 마라.
'정보처리기사처럼 같은 답을 외우면 충분하다'는 가정으로 앱을 설계하지 마라.

콘텐츠 출처 유형을 구분하라:

official_released: 시행기관이 실제 공개한 문항. 공식 출처와 이용 조건이 확인된 경우에만 사용.

licensed_reconstruction: 복원·재구성 문항. 제공자와 이용 허락 범위를 확인하고 정확성도 별도로 검증.

original_practice: 공개 출제기준과 개념을 바탕으로 독자적으로 제작한 연습문제.

original_mock: 독자적으로 제작한 실전 형식 모의문제.

user_private: 사용자가 직접 작성·입력한 개인 자료. 출처·검증 상태를 구분하고 자동 재배포하지 않는다.

출처 종류와 검증 상태는 별개 필드다. 출처가 있다고 정답 검증이 끝난 것은 아니다.
이용 권한이 확인되지 않은 책·유료 강의·블로그 문제를 대량 복사하거나 문장만 바꿔 수록하지 마라.
공식 공개 기출을 확보하지 못하면 그 사실을 명시하고 검증된 창작 문제로 기본 학습을 완성하라.
원본이 없는 회차를 생성하거나 '공식 기출 500제' 같은 허위 이름을 쓰지 마라.
권한이 확인된 외부 문항을 나중에 추가할 수 있는 구조를 만들되, 빈 기출 메뉴를 핵심 기능처럼 전시하지 마라.

4. 교육과정과 범위 추적

아래는 출제기준 대조용 초안이다. 최종 공식 범위와 대조해 누락·추가·이동 사항을 기록하라.
교재의 자체 목차를 공식 출제기준 목차로 오인하지 마라.

[1과목: 데이터 모델링의 이해]
A. 데이터 모델링의 이해

데이터 모델링의 이해, 엔터티, 속성, 관계, 식별자.
B. 데이터 모델과 SQL

정규화.

관계와 조인의 이해.

모델이 표현하는 트랜잭션의 이해.

NULL 속성의 이해.

본질식별자와 인조식별자.

[2과목: SQL 기본 및 활용]
C. SQL 기본

관계형 데이터베이스 개요, SELECT문, 함수, WHERE절.

GROUP BY·HAVING절, ORDER BY절, 조인, 표준 조인.
D. SQL 활용

서브쿼리, 집합 연산자, 그룹 함수, 윈도우 함수.

Top N 쿼리, 계층형 질의·셀프 조인.

PIVOT·UNPIVOT, 정규 표현식.
E. 관리 구문

DML, TCL, DDL, DCL.

SQLP 전용·구범위·과도한 튜닝 내용을 SQLD 필수 범위로 섞지 마라.
이해에 필요한 선수지식은 '기초 보충', 시험 밖 내용은 '범위 밖 참고'로 구분하라.

각 세부 학습목표를 다음과 연결하라:
objectiveId → 선수 개념 → 노트 → 암기 퀴즈 → 적용 문제 → 해설 → 복습 규칙 → 검증 근거.
전체 범위에서 비어 있는 항목을 자동 탐지하라.
'개념을 읽었다', '용어를 외웠다', '문제에 적용했다'를 다른 진척도로 관리하라.
중요도는 학습상 중요도와 실제 출제 빈도를 구분하라. 빈도 자료가 없으면 '출제율 80%' 같은 수치를 만들지 마라.

5. 필기형 개념 노트

긴 교과서 원문이나 키워드만 나열하지 마라. 한 학습목표를 이해하고 바로 확인 문제로 넘어갈 수 있도록 구성하라.
모든 정규 노트는 다음 내용을 포함하라:

이번 노트에서 이해할 것.

한 문장 핵심 정의.

전문용어를 풀어 쓴 쉬운 설명.

시험 답안에 필요한 정확한 표현.

작은 사례·표·ERD·SQL 예제 중 적절한 것.

자주 혼동하는 개념과의 비교.

반드시 기억할 내용과 조건·예외.

대표 오해와 반례.

핵심 회상 질문 및 연결 퀴즈.

관련 문제, 이전·다음 개념, 출처·검증 버전.

예시는 정의를 그대로 반복하는 장식이 아니라 해당 개념이 실제로 작동하는 이유를 보여줘야 한다.
정규화는 표의 행만 보고 함수 종속성을 단정하지 말고 업무 규칙·후보키·종속성 조건을 제시하라.
ERD는 관계의 방향, 선택/필수 참여, 카디널리티와 식별 관계를 일관되게 표시하라.

필기 표현:

핵심 단어의 굵게 표시, 밑줄, 절제된 형광펜, 여백 메모, 비교 상자.

설명자가 표시한 중요도는 '필수 암기/주의/핵심' 배지로 표현한다.

사용자의 문제 즐겨찾기 별과 설명자의 중요 표시를 혼동시키지 마라.

모든 문장을 강조하지 말고 강조의 우선순위를 유지하라.

'전체 설명 / 핵심만 / 암기 가리기' 보기 전환을 지원하라.

설명은 실제 텍스트로 구현하고 검색·선택·확대가 가능해야 한다. 노트를 통이미지로 만들지 마라.

사용자 기능:

문장 선택 하이라이트, 밑줄, 메모, 노트 북마크와 개인 메모 검색.

읽던 위치, 접은 영역, 글자 크기와 보기 설정 저장.

콘텐츠 수정 후에도 blockId·인용 텍스트 기반으로 메모를 최대한 유지하고, 재연결 실패 항목을 삭제하지 말고 보관함에 남겨라.

정교한 자유 필기 캔버스는 후순위다. 필수는 필기형 표현과 안정적인 강조·메모 기능이다.

6. 개념 암기 퀴즈와 적용 문제

모든 문항에 학습목표, 평가하는 능력, 정답 근거를 명시하라.

암기 퀴즈:

기본은 한국어 4지선다.

정의↔용어 연결, 혼동 개념 구분, 조건·예외 확인, SQL 한 줄 해석.

선택형 빈칸과 답 가리기 회상 카드는 보조적으로 제공 가능.

타이핑을 하지 않으면 진도가 막히는 구조로 만들지 마라.

적용 문제:

작은 테이블을 보고 SQL 결과·행 수·NULL 여부·오류 여부 판단.

조건에 맞는 SQL 선택, 잘못된 SQL 수정안 선택.

모델링 사례, 정규화와 키·관계 해석.

집계·서브쿼리·윈도우 함수·트랜잭션 상태 추적.

품질 규칙:

기본 단일정답 문항은 정답이 정확히 하나여야 한다.

복수선택은 학습용으로 제공할 때만 선택 개수를 명시하고, 확인되지 않은 실전 형식을 만들지 마라.

문제에 필요한 스키마·데이터·제약조건·DBMS·버전·세션 조건을 빠뜨리지 마라.

의미 있는 오답을 만들고 각 오답의 틀린 이유를 설명하라.

답의 길이, 표현, 문법, 보기 위치만으로 정답을 유추할 수 있는 편향을 검토하라.

보기를 섞을 때 정답은 번호가 아니라 고정 choiceId로 관리하라.

'위의 모두', '①과 ③'처럼 순서 의존적인 보기는 섞기 금지 또는 안전한 재매핑 규칙을 적용하라.

동일한 질문에 숫자·이름만 바꾼 변형은 독립 원문 수로 세지 마라.

생성 시드와 변형 규칙을 기록하고, 변형 후 정답을 다시 검증하라.

v1 콘텐츠 목표:

현행 범위의 모든 학습목표에 완성된 노트와 문제를 연결한다.

개념 확인 150문항 + 적용 200문항 + 별도 모의고사 250문항 = 총 600개의 고유 문항을 목표로 한다.

모의고사 250문항은 50문항씩 5세트로 구성하고 각 세트의 과목 배분을 ExamSpec에 맞춘다.

개념 확인은 학습목표별 최소 3문항을 기본으로 배치하고, SQL 적용 목표는 복수의 다른 풀이 상황으로 검증한다.

숫자는 개발 목표이지 합격을 보장하는 과학적 최소치가 아니다.

수량을 채우려고 부실 문항을 배포하지 마라. 검수 미달 문항은 격리하고 목표 대비 실제 수량·누락 범위를 보고하라.

7. 선생님 수준의 해설: 명확한 평가 기준

'정답은 ②이다. 해당 개념에 따른다' 정도의 해설은 불합격이다.
맞힌 문제에서도 해설을 열 수 있어야 한다.
기본 화면에는 핵심 이유를 보여주고, 자세한 설명을 펼칠 수 있게 하라. 사용자의 펼침 선호를 기억하라.

해설에 필요한 항목:

정답과 핵심 이유.

이 문제가 묻는 개념과 알아야 할 선수지식.

지문에서 먼저 볼 조건.

단계별 풀이와 필요한 중간 표·결과.

각 보기의 옳고 그른 이유.

사용자가 선택한 오답과 관련된 혼동 지점.

기억할 한 문장과 그 문장이 성립하는 조건.

연결 노트와 새로운 확인 문제.

적용할 수 없는 항목은 이유와 함께 생략할 수 있지만, 정답 근거·보기별 판단·연결 개념을 비워두지 마라.
사용자의 오답 하나만 보고 사고 과정을 단정하지 말고 '이 개념을 혼동했을 가능성이 있습니다'처럼 표현하라.
긴 설명 자체를 품질로 평가하지 말고, 초보자가 다음 유사 문제를 혼자 풀 수 있는지 평가하라.

SQL 해설 규칙:

원본 테이블 → 조건 적용 → 중간 결과 → 최종 결과의 흐름을 보여라.

입력에 없던 행·열·값을 해설 과정에서 만들어내지 마라.

NULL, 빈 문자열, 0을 시각적으로 구별하라.

COUNT(*)와 COUNT(열)은 실제로 세는 대상에 표시하라.

OUTER JOIN은 미매칭 행과 NULL 확장, ON/WHERE 조건의 영향을 따로 보여라.

GROUP BY·HAVING·윈도우 함수는 묶음과 계산 대상을 구별하라.

SELECT를 가르칠 때 작성 순서, 논리적 처리 순서, 실제 물리적 실행 계획을 혼동시키지 마라.

'항상 FROM부터 실제 실행된다' 같은 과도한 단순화를 금지한다.

시각화:

최소한 NULL·COUNT, INNER/OUTER JOIN, GROUP BY/HAVING, 서브쿼리, 순위 함수, 트랜잭션에 단계형 해설을 제공하라.

이전 단계 / 다음 단계 / 처음으로 / 전체 보기 버튼을 제공하라.

재생을 기다려야 이해할 수 있는 자동 애니메이션보다 사용자가 직접 넘기는 단계형을 기본으로 하라.

강조 색과 동시에 문장·아이콘·행 표시를 사용하고 모션 줄이기를 지원하라.

교육용으로 미리 검증한 단계 자료는 '해설 단계'로 부르고, 실제 DB 실행 추적이라고 허위 표시하지 마라.

8. SQL 정확성과 DBMS 차이 검증

앱의 학습 기록을 SQLite에 저장하는 것과, SQLD 문항의 정답을 검증하는 것은 별개의 문제다.
SQLite에서 실행됐다는 이유로 Oracle·SQL Server에서도 정답이라고 판단하지 마라.

각 SQL 문항에 dialect, 해당 버전, 스키마, 입력 fixture, 제약, 세션 설정, 예상 결과/예상 오류, 검증 방식을 저장하라.
가능한 문항은 명시한 DBMS에서 검증 스크립트로 실행하고 엔진 버전·명령·결과·실행일을 남겨라.
동일 문법이 여러 엔진에서 같다고 주장하면 실제로 필요한 엔진별 근거를 확보하라.
엔진을 실행하지 못했다면 공식 문서와 독립적인 풀이 검토로 검증하되 '실행 검증'으로 표시하지 마라.
논쟁적·모호한 문항은 공개 학습 세트에서 제외하라.

특히 점검할 항목:

NULL과 UNKNOWN, IS NULL, 비교식과 논리 연산.

COUNT, SUM, AVG 등 집계와 NULL 처리.

NOT IN 서브쿼리에 NULL이 있는 경우, NOT EXISTS와의 차이.

OUTER JOIN의 ON/WHERE 위치와 행 증가·제거.

GROUP BY, HAVING, 집합 연산자와 중복.

ORDER BY가 없는 결과의 순서 비보장, 정렬 기준의 동률.

RANK, DENSE_RANK, ROW_NUMBER의 동률 처리.

윈도우 프레임의 ROWS/RANGE, 기본 프레임과 동률 행.

ROLLUP/CUBE/GROUPING, 실제 NULL과 집계용 NULL.

Top N, ROWNUM, TOP, FETCH의 DBMS·버전별 의미.

문자열·빈 문자열·형 변환·날짜·정규식·문자 정렬 규칙.

PIVOT/UNPIVOT과 계층형 질의의 전제와 문법.

DML/TCL/DDL/DCL, 자동 커밋 설정, 암묵적 커밋과 롤백 가능 범위.

결과 비교기는 행 수, 중복, 열 위치, 데이터 타입, NULL, 숫자 정밀도와 순서 보장 여부를 고려하라.
순서가 보장되지 않으면 중복을 보존하는 다중집합으로 비교하라. set으로 바꾸어 중복을 없애지 마라.
동률 때문에 여러 결과가 가능한 쿼리를 단일 확정 결과로 채점하지 마라. 조건을 명확히 하거나 비결정성을 묻는 문제로 수정하라.

v1에서 범용 SQL 실행기나 Oracle 에뮬레이터를 새로 만드는 것은 필수가 아니다.
검증된 정적 예제·단계형 해설을 우선 완성하라. 선택형 실습실을 추가한다면 별도 임시 DB에서 제한된 SQL만 실행하고 학습 기록 DB에 접근시키지 마라.
사용자가 임의로 입력한 SQL에 미리 저장한 결과를 돌려주면서 실행한 것처럼 속이지 마라.

9. 두 가지 채점 방식과 중간 개별 채점

공통 원칙:

보기 터치 = 답안 선택. 즉시 정답 공개나 자동 다음 문제 이동이 아니다.

명시적 채점 전에 선택을 바꾸거나 문제를 건너뛸 수 있다.

채점 시 확정한 첫 제출 답안과 당시 도움 여부를 보존한다. 최초 터치한 보기를 첫 정답 기록으로 오인하지 마라.

A. 즉시채점 학습

보기 선택 → '이 문제 채점' → 결과·해설.

답을 선택하지 않으면 채점 버튼을 비활성화하고, 별도의 '모르겠어요'는 명시적 무응답 제출로 처리하라.

채점한 답안은 잠근다. 다시 풀기는 별도 학습 시도로 만들고 기존 결과를 덮어쓰지 마라.

B. 전체 풀이 후 채점

각 문항의 임시 답안만 저장하고 정답·해설은 감춘다.

원하는 문항으로 이동하며 아직 채점하지 않은 답안을 바꿀 수 있다.

'전체 제출' 전에 미응답 수·이미 채점한 수를 알려주고 확인을 받는다.

전체 제출 시 미응답은 0점 처리하되 통계에는 '미응답'으로 구분한다.

전체 제출 시점에 각 문항은 정확히 한 번만 공식 제출 기록을 갖는다.

C. 전체 풀이 도중 현재 문항만 즉시채점

'현재 문제만 채점'을 항상 찾기 쉬운 위치에 제공한다.

현재 문항만 확정·해설 공개하고 다른 미채점 문항의 답안·정답·해설은 그대로 유지한다.

개별 채점한 문항은 잠기고 '채점 완료'가 표시된다.

나중의 전체 제출은 이미 채점한 문항을 재기록하거나 오답 횟수·복습 일정을 중복 반영하지 않는다.

'지금 전체를 채점'과 '현재 문제만 채점'은 위치·문구·확인 절차로 명확히 구별한다.

D. 실전 모의고사에서의 도움 요청

실전 모드는 기본적으로 제출 전 해설·힌트·관련 노트 이동을 막는다.

사용자가 중간 개별 채점을 원하면 '연습 모드로 전환됩니다'를 확인받아 같은 세션을 혼합 연습으로 전환한다.

기존 답안과 진행은 보존하고, 해당 세션은 순수 실전 진단 지표에서 제외한다.

도움을 본 뒤 다시 실전 미열람 상태로 되돌릴 수 없게 하라.

상태 모델 예시:
UNANSWERED → DRAFT_SELECTED → GRADED_CORRECT / GRADED_WRONG / GRADED_UNANSWERED.
EXPLANATION_VIEWED와 HINT_USED는 별도 노출 기록이다.
세션 상태와 문항 상태를 분리하고 허용 전이·불변식을 명시하라.
동일 제출 ID에 대한 중복 요청은 무해하게 처리하고, 채점·시도 저장·복습 반영을 트랜잭션으로 묶어라.
빠른 연속 터치, 화면 회전, 앱 종료·재실행 중에도 답안·정답·점수가 바뀌면 안 된다.

10. 별표 문제, 오답, 헷갈린 문제

즐겨찾기 별:

모든 문제 화면·해설·결과 목록에 빈 별을 표시하라.

누르면 채워진 별, 다시 누르면 빈 별. 저장 성공 여부를 사용자에게 명확히 전달하라.

앱을 종료해도 상태가 유지되고 목록·상세·필터의 개수가 일치해야 한다.

'별표 문제만 풀기'를 제공하고 과목·단원·최근 저장순·틀린 횟수로 필터링할 수 있게 하라.

별표 해제는 오답 기록 삭제나 숙달 처리와 무관하다.

별표 세션 도중 별을 해제해도 현재 문항이 갑자기 사라지지 않게 하라. 세션 문항 목록은 시작 시 고정한다.

실행 취소를 지원하고, 화면 리더에 현재 선택 상태와 동작을 전달하라.

서로 독립적으로 관리할 목록:

내가 별표한 문제.

현재 복습이 필요한 오답.

과거에 틀린 모든 문제와 해결 이력.

맞혔지만 헷갈린/찍은 문제.

오늘 예정된 복습.

아직 안 푼 문제.

오답 횟수는 실제 채점 시도에서 증가하고 해설을 열거나 화면을 다시 보는 것만으로 증가하지 않는다.
이후 맞혔다고 과거 오답을 삭제하지 마라. '복습 필요/개선됨' 상태만 갱신하라.
정답 확신도는 '확실함/헷갈림/찍음' 같은 선택적 입력으로 제공하되 매 문제마다 추가 터치를 강요하지 마라.
특정 문제의 정답 암기와 연결 개념의 숙달을 구별하라.

11. 복습과 오늘의 학습

복습 간격은 초기 제품 규칙으로 1·3·7·14·30일을 사용하고 설정 가능하게 하라.
이 간격이 모든 사용자에게 최적이라는 주장은 하지 마라.
오답·헷갈림은 빠른 재학습 대상으로 배치하고, 동일 세션의 즉시 재정답을 장기 숙달로 인정하지 마라.
서로 다른 날의 무도움 정답과 다른 풀이형 문항의 정답을 더 의미 있게 취급하라.
중복 복습 항목을 합치고 어떤 이유로 추천됐는지 설명하라.

홈 화면:

가장 눈에 띄는 '이어서 공부' 버튼.

오늘 복습할 문제 수와 짧은 복습 시작.

다음 권장 개념과 취약 단원.

사용자가 설정한 일일 학습량·목표 시험일.

처음 시작하는 사용자는 바로 1단원으로 들어갈 수 있게 하라.

선택형 진단은 건너뛸 수 있고 강제로 거치지 않는다.

밀린 복습이 많아도 모두 끝내기 전 새 학습을 막지 마라.
오늘 처리할 양과 전체 밀린 양을 구분하고 부담 없이 조정할 수 있게 하라.
진도는 권장 순서만 제안하고 원하는 단원으로 이동할 수 있게 하라.
10·20·50문항과 직접 개수 설정을 제공하되 실제 대상 문항 수를 먼저 표시하라.
필터 결과가 부족하면 중복으로 채우지 말고 가능한 수를 안내하라.

12. 모의고사와 학습 성과 측정

모의고사는 ExamSpec에 따라 문항 수·과목 배점·제한시간·합격 기준을 적용한다.
엄격 모의고사에서는 다른 앱으로 이동하거나 화면을 꺼도 시간이 계속 흐른다.
일반 연습은 일시정지 가능하게 하되 모의고사와 구분한다.
만료 시 한 번만 자동 제출하고 남은 미응답을 0점으로 처리한다.
앱 재시작·프로세스 종료·기기 재부팅 후 타이머 복구와 시계 변경 처리 규칙을 문서화하고 테스트하라.

모의고사용 신규 문항은 첫 응시 전 일반 퀴즈·검색·추천에서 노출시키지 마라.
문항을 공유하는 familyId는 같은 원문·풀이 템플릿의 변형을 뜻한다. 동일 개념 전체를 하나의 family로 묶지 마라.
연습과 첫 실전 진단 간에는 동일·근접 변형 family가 섞이지 않게 검토하라.
예약된 진단 문제를 미리 학습용으로 여는 경우 노출 상태를 영구 기록하고 최초 진단 대상으로 취급하지 마라.

결과 화면:

총점, 과목별 정답 수·득점률, 과락 여부, 미응답, 소요시간.

개념별 취약점과 다음 학습 행동.

오답·헷갈린 문제·별표 문제만 다시 풀기.

신규 문제 첫 제출 성적, 반복 풀이 성적, 도움 사용 성적을 구분.

같은 모의고사의 재응시는 '재응시'로 명시.

표본이 적으면 '판단 자료 부족'을 표시.

내부 문제에서의 성적을 실제 시험 합격 확률로 변환하지 마라.

채점 경계값 테스트의 초기 기대값:

(1과목 4개, 2과목 26개) = 60점, 합격 기준 충족.

(4개, 25개) = 58점, 총점 미달.

(3개, 40개) = 86점이어도 1과목 과락.

(10개, 15개) = 50점, 2과목 과락 및 총점 미달.

(4개, 16개) = 40점, 과락은 아니지만 총점 미달.

(10개, 40개) = 100점.
시험 기준이 바뀌면 설정과 테스트 기대값을 함께 갱신하라.

13. UI·UX 디자인 방향과 주요 화면

컨셉: 차분한 개인 학습 노트. 정돈된 편집 디자인과 읽기 편한 문제집.
일반 관리 대시보드처럼 카드·차트·기능 버튼을 과도하게 늘어놓지 마라.

밝은 테마는 따뜻한 종이색 바탕, 진한 본문, 차분한 청록/남색 계열 포인트를 검토하라.

별표는 구별되는 황금색 계열로 표현하되 색만으로 상태를 전달하지 마라.

어두운 테마는 별도 대비 검사를 수행하고 단순 반전하지 마라.

본문은 읽기 쉬운 한국어 글꼴, SQL은 명확한 고정폭 글꼴을 사용하라.

장문의 본문 전체에 손글씨체를 적용하지 마라.

본문 기본 16~18sp 수준을 검토하고 시스템 글자 확대·앱 글자 설정을 지원하라.

간격, 글자, 모서리, 선, 그림자, 아이콘, 색을 디자인 토큰으로 통일하라.

홈 → 노트 → 퀴즈 → 해설 → 복습으로 시각적 문법이 이어져야 한다.

권장 주요 화면:

홈: 이어하기, 오늘 복습, 다음 학습.

과목·단원: 학습목표, 노트와 문제, 이해·암기·적용 진척도.

노트: 목차, 필기형 본문, 메모, 연결 퀴즈.

문제풀이: 지문·표·SQL·보기·별·채점·이전/다음.

해설: 핵심 이유, 단계별 설명, 보기별 분석, 연결 노트.

복습: 별표/오답/헷갈림/복습 예정 필터.

모의고사: 시작 설명, 문제 이동표, 타이머, 제출, 분석.

설정·기록: 테마, 글자, 학습량, 백업·복원, 콘텐츠 버전·출처.

휴대폰:

한 열 레이아웃, 넉넉한 보기 터치 영역, 주요 학습 버튼은 접근하기 쉬운 위치.

긴 지문 아래에서도 채점 버튼을 찾기 쉬워야 하며 고정 버튼이 콘텐츠를 가리면 안 된다.

태블릿:

공간이 충분하면 목차+노트 또는 문제+해설의 두 영역.

채점 전 해설 영역에 정답이 노출되지 않게 한다.

기기 이름이 아니라 실제 창 너비에 따라 배치하고 분할 화면에서 한 열로 전환한다.

SQL·표:

SQL 들여쓰기·줄번호·문법 강조, 가로 스크롤과 줄바꿈 선택.

표의 머리글·행 구분·NULL 표현, 필요한 경우 전체 화면 확대.

스크롤할 수 있다는 단서 제공. 가로 스크롤과 문제 이동 제스처를 충돌시키지 마라.

정답 보기만 유난히 긴 높이나 다른 서체로 보이지 않게 하라.

모든 화면에 최초·빈 목록·검색 결과 없음·로딩·저장 실패·복구·완료 상태를 설계하라.
빈 상태의 안내 버튼은 실제로 동작해야 한다.
검색은 용어, 한국어/영문 동의어, SQL 키워드, 노트·문제 제목을 지원하고 입력 중 실전 예약 문제를 노출시키지 마라.

14. 접근성·사용 편의성 인수 기준

주요 터치 대상 최소 48dp × 48dp를 기준으로 구현·검사한다.

일반 텍스트 대비 4.5:1 이상을 목표로 하고 큰 글자·아이콘·컨트롤은 적절한 별도 기준을 확인한다.

시스템 글자 크기 200%에서도 핵심 내용과 버튼이 잘리거나 겹치지 않아야 한다.

정답/오답/미응답/별표 상태를 색뿐 아니라 텍스트·아이콘·접근성 설명으로 구별한다.

TalkBack의 읽는 순서, 보기의 선택 상태, 별표 토글 상태, 오류 안내를 검증한다.

키보드 포커스가 보이고 태블릿 외부 키보드에서도 기본 학습이 가능해야 한다.

모션 줄이기, 소리·진동 끄기, 밝은/어두운 테마를 지원한다.

뒤로 가기·화면 회전·분할 화면 전환 때문에 진도나 임시 답안이 사라지면 안 된다.

다른 개념을 잠깐 확인한 뒤 정확히 같은 문제·스크롤 위치로 돌아온다. 실전 도움 제한은 별도로 적용한다.

불필요한 팝업, 자동 다음 문제 이동, 답안 터치와 채점의 혼동을 제거한다.

실제 렌더링한 화면을 캡처해 점검하라. 디자인 문서만 보고 UI 검수를 끝내지 마라.
작은 폰·큰 폰·태블릿 가로/세로·분할 화면·다크 모드·큰 글자 상태를 포함하라.

15. 데이터 구조와 저장 안정성

콘텐츠와 개인 학습 기록을 분리하라. 콘텐츠 교체가 사용자 기록 초기화로 이어져서는 안 된다.
화면 코드에 노트·정답을 직접 대량 삽입하지 말고 스키마가 있는 버전 관리 콘텐츠 팩을 사용하라.
핵심 채점·복습·시험 판정 로직은 UI와 분리하여 독립적으로 테스트할 수 있게 하라.
개인 앱에 과도한 서버·마이크로서비스·의미 없는 모듈 분할을 도입하지 마라.

필요한 주요 모델:

ExamSpec, Subject, Topic, LearningObjective, ConceptNote, ContentBlock.

Question, Choice, Explanation, SqlFixture, ExplanationStep, SourceRecord.

QuizSession, SessionItem, AnswerDraft, GradingSubmission, LearningAttempt.

Bookmark, Annotation, ReviewState, ExposureRecord, ContentIssue, ContentVersion.

문항 필드의 최소 범위:
고정 ID, version, subjectId/topicId/objectiveIds, familyId, 유형, 지문,
표·SQL·보기 choiceId, correctChoiceIds, 해설, 중요도와 근거, 난이도와 근거,
dialect/버전/조건, 출처 종류·이용 조건, 검증 상태·방식·증거,
예약 모의고사 여부, 공개/격리/정정 상태.

시도 기록의 최소 범위:
attemptId, sessionId, questionId/version, 제출한 choiceIds, 당시 보기 순서,
최초 확정 제출 여부, 결과, 도움/해설 노출 시점, 확신도, 활성 풀이시간,
제출 시각, 적용한 ExamSpec/콘텐츠 버전, 복습 반영 여부.

답안·별표·메모·읽던 위치를 필요한 시점에 자동 저장하라.

채점 이벤트의 중복 적용을 DB 제약과 트랜잭션으로 방지하라.

오류 문항 정정 후 과거 답안·점수를 조용히 덮어쓰지 마라. 이전 판정과 정정된 판정을 구분한다.

진행 중 세션은 문제 버전·문항 순서·보기 순서를 고정한다.

콘텐츠 업데이트 중 실패하면 이전 정상 버전으로 복구한다.

SQL 예제용 임시 데이터와 개인 학습 기록은 물리적 또는 접근 제어상 분리한다.

16. 백업·복원·보안·정정

기기 간 수동 이동을 위한 전체 학습 기록 내보내기·가져오기를 제공한다.

백업에는 별표, 오답·시도, 메모·하이라이트, 진도, 설정, 스키마·콘텐츠 버전이 포함된다.

복원 전에 파일 유효성·버전·손상·크기를 검사하고 변경될 항목을 보여준다.

적용 전 로컬 복구 지점을 만들고 원자적으로 적용한다. 실패 시 기존 데이터가 보존되어야 한다.

여러 기기의 동시 자동 병합을 가장하지 마라. v1은 명시적인 전체 복원 정책을 우선 구현하라.

백업을 반복 복원해도 시도와 오답 횟수가 중복되지 않아야 한다.

미지원 미래 버전 파일은 명확하게 거부하고 기존 자료를 손상시키지 마라.

사용자 JSON/텍스트 자료는 실행 코드가 아닌 데이터로 처리하고 HTML·스크립트 실행을 막아라.

기본적으로 학습 기록·메모를 외부에 전송하지 마라. OS 자동 백업 정책도 의도적으로 결정하고 문서화하라.

불필요한 기기 권한을 요청하지 마라. 삭제·초기화는 명확한 확인과 범위 선택이 필요하다.

오류 신고:

각 문제와 노트에 '내용 오류 표시' 기능을 제공하라.

네트워크 전송을 전제로 하지 말고 로컬 검토 목록·내보내기를 지원하라.

오류 의심 문항을 개인 복습에서 제외할 수 있게 하되 기록은 남긴다.

정정 버전, 수정 이유, 영향받은 학습 기록을 확인할 수 있게 하라.

17. 콘텐츠 제작·검수 파이프라인

다음 단계를 코드 검증과 별도로 운영하라:
공식 범위 매핑 → 노트 작성 → 문항 작성 → 독립 풀이 → 공식 문서/실행 검증 → 해설 대조 → 중복·편향 검사 → 앱 렌더링 점검 → 공개.

콘텐츠 작성자가 제시한 정답을 그대로 받아쓰기만 하는 검수를 금지한다.

가능한 경우 다른 검토 역할은 정답표를 보지 않고 문제를 풀고 판단을 비교한다.

같은 AI 계열의 역할 분리가 전문가 검수나 객관적 정답 보장을 뜻하지 않는다. 실제 수행한 검증 방식만 기록하라.

사람이 검수하지 않았다면 '전문가 검수 완료'라고 표시하지 마라.

개념 오류, 복수 정답, 보기 누락, 실행 불일치, 불충분한 조건, 해설 모순은 공개 차단 사유다.

초안·검토 중·격리 문항은 기본 학습/통계/모의고사에 섞이지 않게 하라.

전체 콘텐츠 자동 검사:

ID·참조 무결성, 중복 ID, 정답 ID 존재, 문항 형식과 정답 개수.

해설 필수 항목·보기별 근거, 비어 있는 표·SQL·예제.

출처와 실제 검증 상태, 학습목표 연결, 예약 문제 누출.

SQL fixture와 예상 결과의 일치, 단계별 결과와 최종 결과의 일치.

원문·근접 변형 중복, 같은 세션 중복, 정답 위치·보기 길이 편향.

표시용 NULL과 실제 null 데이터의 일관성.

오류·정정·구범위 콘텐츠의 실수 노출.

콘텐츠 검수표는 문제 수만 세지 말고 학습목표별 완성도와 검증 근거를 보여줘야 한다.

18. QA와 회귀 테스트

구현자와 다른 관점에서 기능 QA, 콘텐츠 QA, UI QA를 수행하라.
실제 사용 가능한 서브에이전트가 있으면 역할·담당 파일을 나누고 교차 검토하라.
지원하지 않으면 순차적인 검토 패스로 수행하고, 존재하지 않는 에이전트 회의나 테스트 결과를 꾸며내지 마라.

단위 테스트:

ExamSpec 점수·과락·미응답 경계값.

현재 문항 채점과 전체 제출의 동일 판정 경로·중복 방지.

답안 선택/수정/잠금/다시 풀기 상태 전이.

보기 섞기 이후 정답·해설 매핑.

별표 상태와 필터, 복습 중 별 해제.

복습 일정, 중복 일정, 같은 날 재풀이와 도움 사용 구분.

최초 진단·반복·도움 사용 통계 분리.

순서 없는 SQL 결과의 중복 보존 비교.

통합 테스트:

앱 종료 후 답안·별표·메모·스크롤·세션 복원.

DB 마이그레이션과 콘텐츠 업데이트 후 기록 보존.

정상·손상·다른 버전 백업 복원, 실패 시 롤백.

제출 직전·직후 실패, 빠른 연속 클릭, 중복 이벤트.

타이머 만료·백그라운드·재시작·기기 시간 변경.

콘텐츠 정정 후 과거 시도·현재 세션의 일관성.

필수 E2E 시나리오:

설치 → 오프라인 첫 실행 → 노트 → 개념 퀴즈 → 오답 해설 → 복습.

문제 별표 → 종료 → 재실행 → 별표만 풀기 → 해제 → 목록 확인.

전체 풀이 모드에서 여러 답안 저장 → 현재 문항만 채점 → 다른 문항 유지 → 전체 제출 → 중복 채점 없음.

채점하지 않은 답안 변경은 허용되고, 채점 후 원래 제출 기록은 바뀌지 않음.

엄격 모의고사에서 개별 채점 요청 → 연습 전환 확인 → 최초 실전 지표 제외.

제한시간 만료 → 미응답 포함 자동 제출 → 재실행 후 중복 제출 없음.

틀린 문제 재정답 → 현재 복습 상태 개선 → 과거 오답 이력 유지.

노트 메모·하이라이트 → 콘텐츠 업데이트 → 유지 또는 복구 보관함으로 이동.

백업 → 깨끗한 별도 앱 데이터 환경에 복원 → 모든 주요 기록 비교.

큰 글자·다크 모드·태블릿 분할 화면에서 전체 학습 동선 완료.

검색·관련 문제·추천에서 아직 열지 않은 예약 모의고사 문항 노출 없음.

정답 공개 전 UI·접근성 레이블·숨겨진 패널에서 정답이 노출되지 않음.

추가 검증:

재현 가능한 난수 시드로 답안 선택·이동·채점·별표·중단을 섞은 상태 기반 테스트를 실행하라.

지연·실패·낮은 저장 공간 등 실제 실패 조건을 주입하라.

주요 화면 캡처의 잘림·중첩·대비·스크롤·클릭 영역을 확인하라.

시작 시간·화면 전환·긴 목록 성능은 환경과 측정 방법을 함께 기록하고 근거 없는 숫자를 보고하지 마라.

모의 사용자의 정답률을 임의로 가정한 시뮬레이션으로 실제 학습 효과나 합격률을 입증하지 마라.

19. 개발 방식: 단계별 작동하는 결과물

단계마다 설계 → 구현 → 자동 검증 → 실제 화면 확인 → 수정 → 회귀 테스트를 수행하라.
모든 기능을 문서로만 다 정리한 뒤 마지막에 처음 실행하는 방식은 피하라.

단계 1: 시험 근거·범위 매핑, 기술 선택, 데이터·채점 상태, 디자인 토큰, QA 계획.
단계 2: 대표 노트 1개와 문항 8~10개로 노트→퀴즈→두 채점 방식→현재 문항만 채점→해설→별표→복원까지 실제 연결.
단계 3: 두 과목 전체 노트·개념 퀴즈·적용 문제를 검수된 콘텐츠 묶음 단위로 확장.
단계 4: 오답·헷갈림·간격 복습·검색·개인 필기·학습 홈 완성.
단계 5: 독립 모의고사, 노출 구분, 성과 분석, 백업·정정 완성.
단계 6: UI 정교화, 접근성·기기 크기 점검, 콘텐츠 전수 검사, 회귀 테스트, 배포 파일 생성.

초기 소규모 완성 흐름은 설계 검증용이지 최종 납품이 아니다.
문제 수만 늘리거나 디자인만 바꾸는 식으로 핵심 기능 미완성을 숨기지 마라.
진행 상황은 완료 항목, 실제 검증 결과, 발견한 위험과 해결 내용 중심으로 간결하게 보고하라.
실행 한도·권한·환경 때문에 중단되면 실제 변경 파일, 실패 로그, 남은 요구사항과 다음 실행 지점을 정확히 저장하라.
백그라운드에서 계속 작업 중이라고 말하지 말고, 실제 수행한 범위만 보고하라.

20. 최종 산출물과 완료 판정

필수 산출물:

빌드 가능한 전체 소스와 의존성 고정 정보.

설치·실행 가능한 APK. 서명·배포 조건이 없으면 디버그 빌드임을 명시하고 릴리스 완료라고 하지 마라.

실행·빌드·테스트·백업·콘텐츠 추가·정정 방법을 담은 README.

AGENTS.md와 요구사항 추적표, 핵심 설계·결정 기록.

전체 노트·문항·해설·SQL fixture·출처 레지스트리와 버전 관리 콘텐츠 팩.

실제 실행 가능한 콘텐츠 검증·테스트 스크립트.

시험 기준 근거, 범위 커버리지, 콘텐츠 검수 보고서.

UI 캡처와 접근성·기기 크기 점검 결과.

실제 테스트 명령·실행 환경·성공/실패/미실행을 구분한 QA 보고서.

정정 이력, 알려진 한계, 미해결 항목 목록.

완성판 판정 조건:

사용자 요구사항이 실제 화면·데이터·테스트에 연결되어 있다.

현행 출제기준의 모든 필수 학습목표에 내용 있는 노트·문제·해설이 있다.

노트·문제·복습·모의고사·별표·두 채점 방식·중간 개별 채점이 오프라인에서 동작한다.

콘텐츠 공개 정책, 정답 검증, 예약 모의고사 구분이 지켜진다.

점수 오류, 정답 오류, 데이터 소실, 정답 조기 노출, 중복 채점 등 치명적 결함이 해결되어 있다.

사용을 막는 UI 결함과 핵심 학습 동선의 미완성이 없다.

앱 종료·회전·백업·마이그레이션 후 학습 기록이 보존된다.

실제 실행한 빌드·테스트 증거가 있다.

목업, TODO, 빈 화면, '추후 구현', 검수하지 않은 대량 생성 문항으로 필수 기능을 대체하지 않았다.

최종 보고는 다음을 구분해서 작성하라:

실행/설치 방법과 생성 파일의 실제 경로.

구현 완료/부분 완료/미구현 요구사항.

과목별 노트·고유 문제·모의고사·검수/격리 문항 수.

실행 검증, 문서 검토, AI 교차 검토, 사람 검수의 실제 수행 범위.

통과/실패/미실행 테스트와 근거.

남은 위험과 사용자가 알아야 할 제약.

테스트할 장치나 환경이 없으면 그 부분은 미검증이다.
완료 조건을 충족하지 못했으면 설치 가능한 부분이 있더라도 '완성품 검증 완료'라고 하지 마라.

이제 저장소와 실행 환경 확인부터 시작하고, 위 순서로 실제 파일 작성·개발·검증을 수행하라.
